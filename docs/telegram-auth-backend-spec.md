# ТЗ для Русланбека: бесшовный вход через Telegram Mini App

**Дата:** 23.09.2026
**Кому:** Русланбек (бэкенд)
**От кого:** фронтенд Yoldosh Web
**Статус:** веб-фронт готов, ждёт эндпоинты

---

## 1. Задача

Русланбек, нужно дописать бэкенд под Telegram Mini App. Веб-фронт со своей стороны
уже готов — не хватает двух эндпоинтов и правил связывания аккаунтов.

Что должно получиться для пользователя:

1. Открыл мини-апп из бота — **попал сразу в приложение**, без ввода номера и без SMS-кода.
2. Через неделю зашёл на `yoldosh.uz` с ноутбука, ввёл свой номер, получил OTP —
   **попал в тот же самый аккаунт**. Те же поездки, брони, кошелёк, история чатов.
3. Поставил нативное приложение, вошёл по тому же номеру — **снова тот же аккаунт**.

### Главное требование

> **Номер телефона — единственный идентификатор пользователя.
> Telegram — это способ входа, а не отдельная личность.**

Если у одного человека появятся два аккаунта (один «телеграмный», другой «по номеру») —
задача провалена, даже если вход технически работает. Это и есть тот рассинхрон,
которого мы избегаем: поездки в одном аккаунте, деньги в другом.

## 2. Почему нельзя заводить аккаунт по одному `telegram_id`

Самое очевидное решение — «пришёл `initData`, нет такого `telegram_id` → создаём
нового пользователя» — как раз и создаёт рассинхрон. Разберём на живом примере:

| Шаг | Что делает пользователь | Что происходит при «аккаунте по telegram_id» |
|---|---|---|
| 1 | Открывает мини-апп впервые | Создаётся User A с `telegram_id=123`, **без номера** |
| 2 | Бронирует поездку в мини-аппе | Бронь падает в User A |
| 3 | Заходит на сайт, вводит `+998901234567`, OTP | Пользователя с таким номером нет → создаётся **User B** |
| 4 | Ищет свою бронь на сайте | Её нет. Она в User A, куда с сайта не попасть никогда |

Дальше становится только хуже: деньги на кошельке User A, рейтинг у User B, водитель
пишет в чат User A, а пользователь читает уведомления User B.

**Вывод: аккаунт без номера создавать нельзя ни при каких условиях.**
Пока номер неизвестен — сессию не выдаём, а просим номер (см. §5). Это одна
дополнительная кнопка при первом входе, зато один аккаунт на всю жизнь.

## 3. Изменения в модели данных

В таблицу `users` (или где у тебя лежит профиль):

| Поле | Тип | Ограничения | Зачем |
|---|---|---|---|
| `telegram_id` | `bigint` | `UNIQUE`, `NULL` по умолчанию | id пользователя в Telegram. Уникальный: один Telegram-аккаунт не может вести в два профиля |
| `telegram_username` | `varchar(64)` | `NULL` | Для поддержки и админки, не для идентификации — юзернейм меняется |
| `telegram_photo_url` | `text` | `NULL` | Аватар из Telegram, если у нас своего нет |
| `telegram_linked_at` | `timestamptz` | `NULL` | Когда привязали. Пригодится при разборе спорных ситуаций |
| `phone_verified_via` | `enum('otp','telegram','bot')` | `NULL` | Как подтвердили номер. Нужно для аудита и для решения конфликтов |

Индексы:

```sql
CREATE UNIQUE INDEX users_telegram_id_uniq ON users (telegram_id) WHERE telegram_id IS NOT NULL;
```

Частичный индекс — чтобы множество `NULL` не мешало уникальности.

**Важно:** `phoneNumber` остаётся `NOT NULL UNIQUE`, как сейчас. Никаких послаблений
ради Telegram — это и есть страховка от второго аккаунта.

### Отдельно про `registration_source`

У вас в ответах уже приходит `registration_source` со значениями `"user"` и `"from_bot"`.
Значит, часть пользователей уже заведена ботом. Проверь, пожалуйста:
**хранится ли у таких записей номер телефона и `telegram_id`.** Если да — половина
работы сделана, и для них первый вход в мини-апп будет мгновенным без всяких
запросов контакта.

## 4. `POST /auth/telegram` — вход по initData

Основной эндпоинт. Фронт зовёт его сразу при открытии мини-аппа.

### Запрос

```json
{
  "initData": "query_id=AAH...&user=%7B%22id%22%3A123...%7D&auth_date=1790000000&hash=abc123...",
  "guestId": "6fc69426-2ce9-4b26-ad19-32b21f1e6828"
}
```

- `initData` — строка **как есть** из `window.Telegram.WebApp.initData`. Не разбирай её
  на фронте и не доверяй разобранному: подпись считается по исходной строке.
- `guestId` — опционально, гостевой id из localStorage (см. §9). Нужен, чтобы привязать
  активность до регистрации к созданному аккаунту — ровно так же, как это уже работает
  в `/auth/request-otp`.

### Алгоритм валидации подписи

Это обязательная часть — без неё любой может подделать `initData` и войти под чужим
аккаунтом.

```
1. Распарсить initData как query string, URL-декодировать значения.
2. Вынуть и отложить поле `hash`.
3. Собрать data_check_string: оставшиеся пары "key=value",
   отсортированные по ключу по алфавиту, склеенные через "\n".
4. secret_key = HMAC_SHA256(key="WebAppData", message=<BOT_TOKEN>)
5. computed  = HEX(HMAC_SHA256(key=secret_key, message=data_check_string))
6. Сравнить computed с hash — constant-time сравнением (не обычным ==).
7. Проверить свежесть: now - auth_date <= 24 часа (лучше 1 час, см. §8).
```

Обрати внимание на порядок аргументов в п.4: ключ — это литеральная строка
`"WebAppData"`, а сообщение — токен бота. Это частая ошибка, из-за которой подпись
не сходится.

### Ответы

**A. Номер известен — выдаём сессию** (основной случай):

```json
{
  "success": true,
  "status_code": 200,
  "message": "Authorized via Telegram.",
  "data": {
    "status": "authorized",
    "accessToken": "eyJ...",
    "refreshToken": "eyJ...",
    "expiresIn": 3600,
    "user": { "id": "...", "firstName": "...", "phoneNumber": "+998...", "...": "как в /auth/verify-otp" }
  }
}
```

Формат `data` — **точно такой же**, как у `/auth/verify-otp`. Тогда фронту не нужна
отдельная ветка: он кладёт токены и идёт дальше тем же кодом.

**B. Номер неизвестен — просим контакт:**

```json
{
  "success": true,
  "status_code": 200,
  "message": "Phone number required.",
  "data": {
    "status": "phone_required",
    "linkToken": "одноразовый токен, 10 минут, привязан к telegram_id"
  }
}
```

Аккаунт на этом шаге **не создаём**. `linkToken` — короткоживущий токен, чтобы на
следующем шаге не пересылать `initData` второй раз.

**C. Ошибки:**

| Код | Когда |
|---|---|
| `401` | Подпись не сошлась |
| `403` | `auth_date` протух |
| `429` | Слишком частые попытки с одного IP / `telegram_id` |

## 5. `POST /auth/telegram/link-phone` — привязка номера

Вызывается только после ответа `phone_required`.

### Откуда берётся номер — три пути, по убыванию удобства

**Путь 1 (лучший): номер уже есть у бота.**
Если пользователь когда-то нажимал в боте «Поделиться номером», номер у вас уже
хранится. Тогда `/auth/telegram` находит его по `telegram_id` и **сразу возвращает
вариант A** — пользователь вообще ничего не нажимает. Это идеальный бесшовный вход.
Проверь, есть ли такие данные (см. §3 про `registration_source`).

**Путь 2: `requestContact()` в мини-аппе.**
Фронт вызывает `Telegram.WebApp.requestContact()`, пользователь жмёт «Поделиться» —
одно нажатие. Telegram возвращает подписанный ответ, который **валидируется на бэкенде
тем же алгоритмом**, что и `initData`. Номер, полученный так, считается подтверждённым:
его подтвердил сам Telegram, SMS не нужен.

**Путь 3 (запасной): обычный OTP внутри мини-аппа.**
Если пользователь отказался делиться контактом — показываем привычный экран ввода
номера с кодом. Один раз, дальше вход мгновенный.

### Запрос

```json
{
  "linkToken": "из предыдущего шага",
  "phoneNumber": "+998901234567",
  "contactProof": "подписанный ответ requestContact — для пути 2"
}
```

Для пути 3 вместо `contactProof` идёт обычная пара «номер + otp», как в существующем флоу.

### Ответ

Тот же самый, что и вариант A выше: `accessToken`, `refreshToken`, `expiresIn`, `user`.

**Никогда не доверяй `phoneNumber` из тела запроса без доказательства.**
Либо `contactProof` с валидной подписью Telegram, либо подтверждённый OTP.
Иначе кто угодно пришлёт чужой номер и заберёт чужой аккаунт — это дыра уровня
«полный захват аккаунта».

## 6. Правила связывания и разрешение конфликтов

Это ядро задачи. Всё остальное — обвязка.

Когда у нас на руках есть **подтверждённый номер** и **валидный `telegram_id`**:

| # | Ситуация | Что делаем |
|---|---|---|
| 1 | Пользователя с таким номером **нет**, `telegram_id` свободен | Создаём нового пользователя с номером **и** `telegram_id`. `phone_verified_via = 'telegram'` |
| 2 | Пользователь с номером **есть**, `telegram_id` у него пустой | **Привязываем** `telegram_id` к существующему. Новый аккаунт не создаём |
| 3 | Пользователь с номером есть, `telegram_id` у него **тот же самый** | Обычный вход. Просто выдаём токены |
| 4 | Пользователь с номером есть, но у него **другой** `telegram_id` | Человек сменил Telegram-аккаунт. Перепривязываем на новый, старый затираем, пишем в лог |
| 5 | `telegram_id` уже привязан к **другому** номеру | У человека сменился номер в Telegram. Отвязываем от старого пользователя, привязываем к найденному по новому номеру. Пишем в лог |
| 6 | Оба нашлись, но это **разные** пользователи | Коллизия. **Не сливать автоматически** — см. ниже |

### Про случай 6

Это единственная ситуация, где автоматика опасна: слияние двух аккаунтов с
поездками, деньгами и рейтингами — необратимая операция. Предлагаю:

- вернуть `409 Conflict` с понятным сообщением;
- залогировать оба `user_id` в отдельную таблицу `account_merge_requests`;
- разбирать вручную через поддержку.

Если считаешь, что такую коллизию можно получить массово — напиши, придумаем
автослияние с правилами приоритета. Но по умолчанию лучше не рисковать.

### Что логировать

Каждую привязку и перепривязку: `user_id`, старый и новый `telegram_id`, источник
(`telegram` / `bot` / `otp`), IP, время. Когда придёт жалоба «пропал аккаунт» —
это единственное, по чему можно разобраться.

## 7. Матрица сценариев

Полный перебор — проверь, что каждая строка работает:

| Сценарий | Вход | Ожидаемый результат |
|---|---|---|
| Новый пользователь, мини-апп, номер у бота есть | `initData` | Аккаунт создан, сессия выдана. **Ноль действий пользователя** |
| Новый пользователь, мини-апп, номера нет | `initData` → `phone_required` → контакт | Аккаунт создан, сессия выдана. **Одно нажатие** |
| Был на сайте, теперь открыл мини-апп | `initData` → `phone_required` → контакт | `telegram_id` привязан к **старому** аккаунту. Поездки на месте |
| Был в мини-аппе, теперь на сайте по номеру | номер + OTP | **Тот же** аккаунт. Поездки и кошелёк на месте |
| Был в мини-аппе, теперь в нативном приложении | номер + OTP | **Тот же** аккаунт |
| Повторное открытие мини-аппа | `initData` | Мгновенный вход, ничего не спрашиваем |
| Сменил Telegram-аккаунт, номер тот же | `initData` + контакт | Перепривязка, аккаунт тот же (случай 4) |
| Сменил номер в Telegram | `initData` + контакт | Перепривязка (случай 5) |
| Поддельный `initData` | мусор в `hash` | `401`, сессии нет |
| Протухший `initData` | `auth_date` недельной давности | `403` |

## 8. Безопасность

- **Подпись — обязательно.** Валидация `initData` на сервере, constant-time сравнение
  хэша. Без неё эндпоинт превращается в «войти под любым `telegram_id`».
- **TTL `auth_date`.** Telegram рекомендует сутки, но для выдачи сессии это много.
  Предлагаю **1 час**: мини-апп всегда открывается со свежим `initData`, а украденная
  строка протухнет раньше, чем ею воспользуются.
- **Защита от replay.** Хранить использованные `hash` в Redis на время TTL и отклонять
  повторы. Иначе перехваченный один раз `initData` работает до истечения `auth_date`.
- **Rate limit.** На `/auth/telegram` — по IP и по `telegram_id`. На
  `/auth/telegram/link-phone` — жёстче, это точка подбора номеров.
- **`BOT_TOKEN` только в переменных окружения.** Он же секрет для подписи — утечёт токен,
  можно будет выписывать себе любые сессии.
- **`linkToken` — одноразовый**, 10 минут, привязан к конкретному `telegram_id`,
  сгорает после использования.

## 9. Что уже готово на фронте

Чтобы ты понимал, к чему подключаться.

**Гостевые аккаунты — работает.**
При первом заходе на сайт (любая страница, включая лендинг) фронт зовёт
`POST /auth/guest` с `{guestId, fcmToken}` и сохраняет id в `localStorage`.
При запросе OTP этот `guestId` уходит в `/auth/request-otp`. Проверено: id стабилен
между перезагрузками, повторных регистраций нет.

Просьба: **принимать `guestId` и в `/auth/telegram`** тем же способом — чтобы
активность до входа привязывалась к аккаунту и в телеграмном сценарии тоже.

**Telegram Mini App — каркас готов.**
- SDK подключён, режим мини-аппа определяется автоматически, вне Telegram всё выключено.
- При старте: `ready()`, `expand()`, `disableVerticalSwipes()`, цвет шапки под бренд.
- Свайп вниз не закрывает приложение, страница не «резинит».
- Маркетинговые страницы внутри Telegram недоступны — сразу редирект на вход.

**Чего фронт ждёт от тебя:** ровно два эндпоинта из §4 и §5. Как только они появятся,
подключение с моей стороны — один вызов при старте мини-аппа.

**Формат ответов — важно.** Если `data` при успехе будет **байт в байт** как у
`/auth/verify-otp`, фронту не понадобится отдельная ветка кода. Пожалуйста, не меняй
названия полей.

## 10. Чеклист приёмки

Задача считается сделанной, когда проходят все пункты:

- [ ] `POST /auth/telegram` валидирует подпись; поддельный `initData` → `401`
- [ ] Протухший `auth_date` → `403`
- [ ] Повторная отправка того же `initData` → отклоняется (replay)
- [ ] Известный номер → сессия сразу, формат `data` как у `/auth/verify-otp`
- [ ] Неизвестный номер → `phone_required` + `linkToken`, **аккаунт не создан**
- [ ] `POST /auth/telegram/link-phone` не принимает номер без доказательства
- [ ] Все 6 правил связывания из §6 покрыты тестами
- [ ] Коллизия из случая 6 → `409`, запись в `account_merge_requests`
- [ ] Вся матрица §7 проходит вручную на тестовом боте
- [ ] `guestId` принимается и привязывается
- [ ] Привязки логируются
- [ ] `telegram_id` — уникальный индекс, аккаунта без номера в базе создать нельзя
